# Каталог технических спецификаций

Статус: **реализация пока не согласована**. Нет ни одной утверждённой спецификации компонента.

Применять `$specification-engineering` и его шаблон, создавая отдельные RFC/ТЗ по компонентам только после уточнения требований и ключевых архитектурных решений.

В будущих спецификациях (по необходимости) должны быть: публичный composition API, опциональность модулей, границы ответственности Domain/Application, semantics Kafka publisher/consumer, outbox/inbox, Postgres, gRPC, observability/health, конфигурация/безопасность, жизненный цикл, совместимость, интеграционные тесты, примеры сервисов и упаковка.

Для каждого компонента задать **цели и non-goals, поведение, отказы и восстановление, контракты, конфигурацию/defaults, безопасность, диагностику, критерии приёмки и способ проверки**. Статус различать: `draft`, `approved`, `implementation-ready`.

## Общие критерии готовности
- Первый реальный сервис реализуем по принятой архитектуре.
- Второй, другой по типу сервис, не тянет лишние модули.
- Domain не импортирует инфраструктурные типы.
- Поведение при повторной доставке, retry, сбое между DB и Kafka, graceful shutdown и version skew описано.
- Ключевые ADR приняты пользователем.

**Этот README не является готовой спецификацией.**
