# Видение: переиспользуемая платформа .NET-микросервисов

Статус: **исходное намерение пользователя; архитектура ещё не согласована**.  
Дата фиксации: 2026-10-20.

## Проблема
Пользователь планирует создавать несколько .NET-микросервисов и хочет устранить повторяющуюся инфраструктурную обвязку. Новый сервис должен запускаться с минимальным шаблонным кодом, позволять сосредоточиться на Domain, application handlers и бизнес-логике и при этом получать надёжные инфраструктурные возможности через переиспользуемые компоненты.

## Запрошенные направления
- Kafka publisher/consumer и обработка сообщений.
- CQRS: команды, запросы и обработчики.
- Базовые DDD-абстракции, агрегаты и события.
- Интеграции с gRPC и PostgreSQL.
- Структурированное логирование (пользователь упомянул Serilog), единообразный удобный запуск сервисов.
- Исследование идеи силами Codex, архитектурные интервью, рекомендации лучших практик, полная спецификация **до реализации**.

## Желаемый DX — но НЕ утверждённый API

```csharp
// Только иллюстрация. Класс Platform не существует и его дизайн не утверждён.
await Platform.CreateBuilder(args)
    .AddKafka()
    .AddGrpc()
    .AddPostgres()
    .AddSerilog()
    .Build()
    .RunAsync();
```

Подлинная цель: сервис явно включает только необходимые возможности; общие инфраструктурные настройки и жизненный цикл предсказуемы; бизнес-логика не скрыта.

## Предполагаемые критерии успеха — проверить на интервью
- Композиция независимых, подключаемых по потребности модулей.
- Минимум шаблонного кода при прозрачном доступе к стандартным .NET DI/hosting механизмам.
- Управляемые версии пакетов, обратная совместимость и понятный процесс обновления.
- Наблюдаемость, диагностика и восстановление после ошибок в реальном production.
- Тестируемые границы: gRPC-сервис не обязан подключать Kafka или PostgreSQL.

## Пока НЕ согласованы
Целевая версия .NET, имя библиотеки и namespace, ограничения на лицензии, стратегия распространения пакетов, число сервисов, deployment, требования по доступности/нагрузке, слой доступа к БД, глубина DDD и CQRS, семантика Kafka, необходимость Aspire, необходимость общего `Platform` builder, точный API, конкретные NuGet-пакеты и дорожная карта реализации.

## Архитектурные гипотезы для проверки
- Возможно, нужны три слоя: **тонкие service defaults**, **опциональные интеграции**, **шаблон `dotnet new`** — сравнить с альтернативами.
- Прежде чем писать собственный framework, необходимо проверить возможности стандартного .NET и существующих экосистем.
- Domain Events и Integration Events потребуют разных границ ответственности и правил согласованности.
- Сначала спроектировать для одного настоящего сервиса, затем проверить на втором, отличающемся по типу.

## За рамками текущей фазы
- Написание production-кода и NuGet-пакетов.
- Фиксация проприетарного framework до исследования стандартных средств.
- Event sourcing, сложная оркестрация, distributed workflows без реальной необходимости.

## Критерий завершения архитектурного этапа
Согласованные пользователем ADR, обоснованные технологические решения, контракты и спецификации компонентов, сценарии нескольких характерных сервисов, критерии проверки и поэтапный план разработки.
